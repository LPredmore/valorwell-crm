# Architecture rules

- Shared-schema recovery tooling lives in scripts/migration-recovery and never changes production history; current-state baselines require exact version coverage, private secret review and object parity before isolated replay, because historical source is incomplete.
- Private local restores use an operator-only evidence bundle with baseline-time/latest ledger delta, genuine managed reconciliation, no raw diagnostic persistence and explicit owned-stack retention for independent signed-JWT tests; source CI must never require private SQL, because restore inputs and approval remain outside Lovable/GitHub.
- Branch recovery receipts use closed, offline sanitized metadata validation and remain separate from local restore gates; operator-reported SQL/SET ROLE results never prove signed-JWT acceptance, exact parity or production release, because reconstruction drift and historical replay failures may remain.
- Updated branch evidence uses separate versioned receipts and pins available catalog-query/increment bytes in offline CI; synthetic mutating acceptance requires proven server-side egress denial on an authorized owned stack, because source hashes and client firewalls cannot establish hosted execution safety.
- Campaign isolated acceptance must use the authoritative profile_id membership contract and explicitly supplied hash-verified draft correction, because adding user_id hides real production dependency failures.

- Edge Function RPC calls must have a tracked migration definition (enforced by scripts/check-edge-rpc-contracts.mjs in CI), because deployed code once depended on unapplied SQL and Gmail sync silently failed.
- Social Media Manager background work (e.g. Schedule Series dispatch) runs inside the `social-media-manager` Edge Function behind a cron-secret action, because Supabase does not bundle imports across function directories.
- Schedule Series planning rules live in pure `handlers/series-core.ts`; I/O stays in `handlers/series.ts`, so the rules stay unit-testable without a database.
- Automatic Shorts thumbnail uploads are gated per YouTube account by `ai_operations_social_settings.metadata.shorts_thumbnail_api` and decided only in `_shared/youtube-publish/shorts-thumbnail.ts`, because an API 200/hasCustomThumbnail is not proof a Shorts thumbnail is visible; enabling requires a recorded test run plus human visual confirmation.
- Public asset writes require object tenant metadata matched to trusted JWT app_metadata, tenant membership and CRM write capability. Forward migrations live in supabase/migrations. Legacy untagged objects retain reads but deny writes until independently verified attribution; never guess ownership.
- Sensitive staged SQL awaiting release lives in supabase/staged-migrations (never auto-applied); owner-only private notes are gated by a single-profile allowlist in private schema, never by role, because roles can be granted to others later.
